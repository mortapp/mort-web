# MORT Auth Flow Improvement — Plan

## Scope and implementation

Ship one conversion-focused change: when an unauthenticated visitor opens a protected `/app` route, preserve that in-app destination through the login/signup handoff and make the next steps visible as a compact MORT journey rail. Signup explains account creation → onboarding → review-gated access. Login specifically returning to onboarding highlights sign-in → resume setup → review-gated access. The Supabase proxy will forward the original app path to server components using a request-only header; the auth guard will validate that it is a same-site `/app` path before placing it in `next`. Login/signup already preserve safe `/app` destinations through email and Google OAuth, so those handlers remain the source of truth.

Add a compact, accessible “Next step” cue to the auth shell only for the onboarding return case. Preserve the existing MORT black/silver identity and real `Logomark`; avoid inventing new imagery. Keep all signup field names/order, DOB age gate, role choices, Google and email actions, legal copy, onboarding RPCs/steps, account-review disclosure, and dashboard authorization unchanged.

## Project structure

- `proxy.ts` / `lib/supabase/proxy.ts`: forward the original protected path to downstream server components alongside the existing Supabase session-cookie refresh.
- `lib/auth.ts`: derive and validate a same-site `/app` return path; redirect unauthenticated visitors to `/login` with that `next` value.
- `app/(auth)/login/page.tsx`, `app/(auth)/signup/page.tsx`, and `components/auth-shell.tsx`: show the guided journey and a focused continuation cue for onboarding without changing form contracts.
- `globals.css`: scoped responsive and focus-visible styling for that cue.
- `scripts/onboarding-v2-contract.test.mjs`: assert that the route handoff and protected onboarding contracts stay intact.

## Follow-up — adult ID discovery, camera capture, file import, and phone QR

Mode: Extension. Preserve the existing MORT editorial black/silver interface, real logomark, onboarding and verification routes, one-case review workflow, age-band rules, server-side file validation, private storage, guardian invite tools, and staff-only decision path. Improve discoverability with a direct adult CTA on the onboarding requirements card and a persistent Identity verification item in the account sidebar. On `/app/verify`, keep the ordinary file picker visible as the cross-browser baseline and add optional, user-initiated camera capture. Permit a person to capture or import up to two image files (front and optional back); combine two supported browser-readable images locally into one JPEG so the existing one-object RPC remains unchanged. Keep a supplied single PDF as a direct upload option. All final files remain subject to the existing 10 MB server-side limit and MIME allowlist; add WebP only because the deployed private bucket and RPC already allow it.

Offer a phone QR that contains only the current same-origin `/app/verify` URL. It does not contain ID data, an authentication token, or a transfer-session secret, and it must not be described as encrypted. It only opens MORT on a phone; the person must sign in to the same account there before using the phone's own camera or file picker. A private no-login transfer is explicitly out of scope because the backend has no short-lived, one-time, user-bound transfer session. Never upload an image during camera capture or QR creation.

Project structure: `app/app/onboarding/page.tsx` owns the adult “Upload your ID” CTA; `components/app-shell.tsx` adds the authenticated Identity verification link; `app/app/verify/page.tsx` keeps the existing status/history and guardian flows while rendering `components/verification-uploader.tsx`; `components/phone-verification-qr.tsx` renders the QR client-side using `qrcode.react` 4.2.0 and a same-origin route only; `app/app/verify/actions.ts` remains the authenticated server boundary for MIME/size validation, private storage, registration RPC, and cleanup; `next.config.ts` changes only `camera=()` to `camera=(self)` while leaving microphone and other restricted capabilities disabled; `app/globals.css` contains responsive/focus-visible styles; `scripts/verification-upload-cleanup.test.mjs` and `scripts/onboarding-v2-contract.test.mjs` add regression coverage.

Design Read: adult account verification as an extension for MORT members using desktop or phone; visual language is the current dark editorial tool interface; variance 3/10, motion 2/10, density 5/10, asset dependence 1/10, brand fidelity 10/10. Narrative role is the high-trust action after identity requirements; viewing distance is a phone or laptop; temperature is calm, explicit, and protective; capacity is one visible upload path with optional camera and phone switch, not a new onboarding step. Use MORT ink/silver tokens, Plus Jakarta Sans, 4px spacing multiples, existing 12–22px surfaces and the real `public/mort-mark.svg`; leave global color and typography unchanged. Interaction is opt-in: camera starts only after a button press and stops immediately after capture, close, or unmount; show preview/retake and clear unsupported/permission-denied fallback copy; honor reduced motion. Brand essence: a safe youth marketplace that makes account trust requirements concrete; personality: direct, protective, practical. Voice examples: “Use your camera or choose a file.” “Your ID is not included in the QR code.”

Storage findings (read-only, no document objects accessed): production Supabase project `mort p` (`jxbnrkasktbhtiujkhay`) reports `verification-evidence` as private with a 10,485,760-byte limit and allowed MIME types JPEG, PNG, WebP, PDF, and HEIC. Its policies permit authenticated insert to the caller's folder, read by the owner or authorized staff, and narrowly constrained cleanup of an unregistered owner UUID object. The verification RPC accepts a single evidence path, allows one active case, and rate-limits submissions; no client or schema change may bypass those controls.

Browser facts checked against [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) and the [MDN camera Permissions-Policy directive](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy/camera): camera access requires a secure context and the person's permission; a restrictive policy can block it, and denial or missing devices must leave the file-picker path usable. `camera=(self)` scopes policy permission to MORT's own origin; it does not grant user permission. The [qrcode.react README](https://github.com/zpao/qrcode.react/blob/trunk/README.md) documents the `QRCodeSVG` component and accessible `title` prop.

Highest-risk change: camera permission is blocked by the existing `camera=()` response policy and may still be denied or unavailable in a browser. Mitigation: change only that directive to `camera=(self)`, request access only after an explicit click, stop tracks reliably, keep the file picker as the primary fallback, and retain server-side validation. QR privacy risk: QR scanning could be mistaken for authentication or encryption. Mitigation: encode only the public route and state plainly that same-account sign-in is still required and no ID is in the QR. Rollback: remove the camera/QR component and restore `camera=()`; keep the route CTA, existing file picker, storage policies, and review RPC.
